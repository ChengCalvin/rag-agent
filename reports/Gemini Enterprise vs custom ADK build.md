# Keep the ADK build, rent Gemini Enterprise later

For NovaMart's customer-support agent, the custom ADK build is the right primary path, and Gemini Enterprise is at most an optional staff-facing front end added later. Gemini Enterprise is licensed per employee seat. No source reached says external customers may hold seats, and the one Google product built for customer-facing agents (Gemini Enterprise for Customer Experience, priced per session) is a different product. The prototype's core invariants also fit the platform poorly. Per-user authorization in Gemini Enterprise lives in source ACLs and workforce identity, not in your code. Workflow Builder has no code step, so the numeric confidence composite and outcomes A-E cannot be expressed natively. The platform's own LLM, not your fixed pipeline, picks tools when you connect a custom MCP server. Registering the existing ADK agent keeps the pipeline and guard, but how the user's identity reaches tool code is the least documented and most contradictory part of the platform. Hosting for the custom build is cheap, roughly **$130 to $480 per month at 10,000 conversations** on stated assumptions, against about **$5,000 per month** for per-session customer-experience pricing. The cost is engineering ownership. The recommendation is custom ADK only now, with the hybrid kept as a gated option once external licensing and the identity hand-off are confirmed in writing. A Gemini Enterprise-only build is not recommended.

## Corrections to the earlier report on launch stages and identity

This report builds on the earlier overview of Gemini Enterprise, and the newer release-note research changes four of its statuses. **A2A agent registration is now GA (17 August 2026)**, and three-legged OAuth through the Agent Identity auth manager for ADK A2A agents on Agent Runtime went GA on 13 November 2026 ([release notes](https://docs.cloud.google.com/gemini/enterprise/docs/release-notes)). The earlier "Preview" label came from a registration page that predates that release. **ADK agent registration on Agent Runtime has been GA since 20 April 2026**, including cross-project agents ([release notes](https://docs.cloud.google.com/gemini/enterprise/docs/release-notes)). **The Custom MCP server data store went GA on 7 August 2026** after a public preview on 22 July. Later entries added `citation_mappings` (GA 16 October) and VPC connectivity with static-IP egress (GA 27 October) ([release notes](https://docs.cloud.google.com/gemini/enterprise/docs/release-notes)). The earlier report listed the Custom MCP connector as public preview, so that status is superseded. **Workflow Builder is GA as of 3 September 2026.** An earlier "GA with allowlist" entry from 18 June is superseded by the later plain GA ([release notes](https://docs.cloud.google.com/gemini/enterprise/docs/release-notes)). Two statuses remain unresolved: the tool-authorization resource (OAuth for ADK agents) has no launch stage on the pages read, and sharing of custom registered agents was last seen as Public Preview in a December 2025 entry. The final roughly 16,000 characters of the release notes were not read, so later entries could change any of these.

The second correction is a conflict, not a status change. The registration page says "ADK agents receive the user's email address from Gemini Enterprise" for personalization and permissions, and it describes no state key, `tool_context` field or `user_id` mapping ([register ADK agents](https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-adk-agent)). The accepted answer in the ADK maintainers' discussion (April 2026) says the opposite for the default case. Gemini Enterprise calls Agent Runtime with its own service identity and **"passes no end-user information"**. The user's identity arrives only if an admin attaches a tool authorization, after which the user's access token (an Entra token in the Entra example) is forwarded ([adk-python discussion 3488](https://github.com/google/adk-python/discussions/3488)). The more specific and more recent source should be trusted, so this report treats the email claim as **unverified and probably true only when authorization is configured**. The earlier report's conclusion that registered agents "receive the user's email" should be read that way. A live test settles it.

Several earlier facts still hold. Editions are Business, Standard, Plus, Frontline and Pay-as-you-go, with no list prices on Google's own pages. Seat prices (Business about $21, Standard about $30, Plus $30 to $50 depending on source) come from secondary sources ([Dupple](https://dupple.com/learn/gemini-enterprise-pricing); [ecorpit](https://ecorpit.com/gemini-enterprise-agent-platform-cost-breakdown-2026/)). Official overage rates are documented: **$0.10 per Assistant query, $4.00 per Deep Research query and $5 per GiB-month of storage** ([overages](https://docs.cloud.google.com/gemini/enterprise/docs/overages)). Authorization is "enforced by the platform, not by your code". Users see only what they can already access in the source system, and custom data carries `acl_info` readers, with at most 3,000 readers per document ([identity provider doc](https://docs.cloud.google.com/gemini/enterprise/docs/configure-identity-provider); [custom-data access control](https://docs.cloud.google.com/gemini/enterprise/docs/identity)). One earlier gap is now partly closed. The earlier report found no confirmed Canadian residency, but a locations page lists **`ca` as an in-country location with at-rest and ML-processing residency, access "GA with allowlist"** through the Google account team ([locations](https://docs.cloud.google.com/gemini/enterprise/docs/locations)). That page does not say which editions support `ca`, and it excludes Gemini 3.8 Flash and Claude models there.

## Tools and authorization work, but the platform does not own your principal

**Custom tools and APIs: yes, three routes.** A Custom MCP server connector lets Gemini Enterprise call your backend. It supports StreamableHTTP only and needs HTTPS with a publicly trusted certificate unless routed through Agent Gateway. All actions are off by default, and each call needs user confirmation unless the tool sets `readOnlyHint` ([custom MCP setup](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)). The action cap is 100 on Google's page, against 150 in one guide (unresolved). An ADK agent on Agent Runtime can be registered and then runs your own tool code. An A2A agent can be registered too. The third route is the best fit for the prototype's three tools (`search_policy`, `get_order_status`, `check_return_eligibility`). It is also the route with the thinnest documentation of how a user reaches that code.

**Per-user authorization in code: yes inside code you host, no inside the platform's own index.** In the index, the model is source ACLs plus identity-provider resolution. No documented mechanism injects arbitrary per-query filter logic. In code you host, three mechanisms exist. For a Custom MCP server, Gemini Enterprise sends the user's OAuth token intact in the `Authorization` header, plus a Google-signed service ID token in `X-Serverless-Authorization` that only Cloud Run consumes ([custom MCP setup](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)). For an A2A agent, the `Authorization` header carries `Bearer USER_OAUTH_TOKEN`. Google `ya29` access tokens are opaque, so they must be validated through tokeninfo (`aud`, `scope`). Agent-card `securitySchemes`, API keys and static custom headers are not supported ([register A2A agents](https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-a2a-agent)). For a registered ADK agent, a January 2026 maintainer comment says the forwarded access token lands in session state, no OIDC scheme is needed, and ADK has no built-in way to inject it into tool calls ([discussion 3488](https://github.com/google/adk-python/discussions/3488)). A Google-hosted community sample reads it from `context.session.state` through a custom auth provider ([aaauth-adk-credentials](https://googlecloudplatform.github.io/iam-federation-tools/aaauth-adk-credentials)). No official page names the state key. No page states that the model cannot supply or alter the credential. The ADK context docs do not say whether the model can influence `user_id` or state ([ADK context](https://adk.dev/context/)).

What this means for the prototype's invariant, a principal the model never supplies, is that the invariant survives but is not guaranteed by the platform. The pattern is a `before_tool_callback` or tool body that reads the token from `tool_context.state`, validates its signature, derives the customer principal, ignores any identity-like model argument, and **fails closed when no token is present**. That last point matters because, without admin-configured authorization, the agent is effectively anonymous. The mapping from a workforce or Entra token to a NovaMart customer or order owner is still your code's job. The harder limit is population. Gemini Enterprise identities are workforce identities, so a design where retail customers authenticate and see only their own orders does not fit per-document ACLs or the seat model. Two smaller issues: an A2A or ADK agent needing user OAuth cannot continue the same run after authentication, so the user authenticates and a new run starts ([known issues](https://docs.cloud.google.com/gemini/enterprise/docs/workflow-builder/known-issues)). Model Armor does not protect registered ADK or A2A agents from console settings and must be called from agent code ([register ADK agents](https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-adk-agent)).

**Deterministic routing and confidence gating: not natively.** Workflow Builder has three documented step types: Gemini Agent (text or structured JSON, Gemini 3.0+ only), Condition (operators such as contains, equals and greater than, combinable with AND/OR) and Request info (human input). There is **no code step** and no documented expression syntax ([workflow agents](https://docs.cloud.google.com/gemini/enterprise/docs/workflow-builder/workflow-agents)). The overview mentions loops, but no loop step appears in the step table. Loop bounds and exit conditions are undocumented, and whether "greater than" works on numbers rather than strings is not stated. A Condition on a numeric field is plausible. But the weighted composite across retrieval, validator and policy signals, the retrieval-validator retry loop and the outcome mapping A-E would have to be computed inside an imported ADK agent or an MCP tool, with Conditions branching only on returned fields. Branching on an LLM-produced JSON value is deterministic routing on a nondeterministic value. Discovery Engine's `rankSignals` expose several numeric signals, but no documented score range, cross-query comparability or cutoff parameter was found. The check-grounding threshold (default 0.6) is an API feature and not available inside the chat app ([check grounding](https://docs.cloud.google.com/generative-ai-app-builder/docs/check-grounding)). They are weak inputs for a calibrated gate and do not replace the prototype's composite. With a Custom MCP connector alone, Gemini Enterprise's own LLM chooses which tools to call and in what order, so the fixed five-agent pipeline is lost. Registering the whole ADK app preserves it in principle. ADK constructs (`SequentialAgent`, `LoopAgent`, callbacks, a custom `BaseAgent`) should run as written because the registered agent is the deployed ADK app, and Agent Runtime lists ADK under "Full integration" ([Agent Runtime](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime)). But no official page confirms each construct. Nothing was found on chat-turn timeouts, streaming, or whether intermediate sub-agent events show in the UI. This needs a roughly one-day proof of concept.

## The custom path is a small step from adk web, with persistence and identity as the real work

ADK documents three hosting targets ([adk.dev/deploy](https://adk.dev/deploy/)). **Cloud Run** is the lowest-effort path: `adk deploy cloud_run` packages the agent and ADK API server, builds with Cloud Build, and takes flags such as `--session_service_uri`, `--artifact_service_uri` and `--with_ui`, with extra gcloud flags such as `--min-instances` passed after `--` ([Cloud Run deploy](https://adk.dev/deploy/cloud-run/)). A numpy index and synthetic data ship inside the image, read-only. **Agent Runtime** (formerly Agent Engine, within the renamed Gemini Enterprise Agent Platform) is fully managed. It deploys via `adk deploy agent_engine` or the SDK with `AdkApp`, auto-creates a managed session resource, and is called through IAM-protected `:query` and `:streamQuery` endpoints, so it is not directly end-user-facing ([deploy](https://adk.dev/deploy/agent-runtime/deploy/); [quickstart](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime/quickstart-adk)). It is the only target from which Gemini Enterprise registration works. How local data files are bundled for `adk deploy agent_engine` was not documented on the pages read. The Agents CLI scaffolds a Dockerfile, Terraform and CI for all three targets ([agents-cli](https://adk.dev/deploy/agent-runtime/agents-cli/)). **GKE** (`adk deploy gke`, Python only) gives the most control and the most work: an existing cluster, Kubernetes roles and manifests, and no documented secret passing ([GKE deploy](https://adk.dev/deploy/gke/)). It is not justified for a small support agent. The effort ordering Cloud Run, then Agent Runtime with Agents CLI, then GKE is my judgment, not an official estimate. GA or Preview labels were not shown on these pages, and the `--deployment-target` naming differs between docs (`agent_engine` against `agent_runtime`), so verify the installed CLI.

Moving from `adk web` changes eight things. First, **the model credential**: free-tier terms let Google use prompts and responses for product improvement and human review, and say not to submit sensitive or personal information. Paid services do not, and in the EEA, Switzerland and UK only paid services may serve end users ([Gemini API terms](https://aistudio.google.com/docs/terms)). The free key is acceptable only for synthetic data. Moving to Vertex is mostly environment variables (`GOOGLE_GENAI_USE_ENTERPRISE=True`, project, location) plus `roles/aiplatform.user`, with model IDs unchanged. Agent Runtime's quickstart is Vertex-based and does not mention API keys. Second, **persistent sessions**: if the session URI is unset, Cloud Run silently falls back to in-memory and loses state. Use managed sessions on Agent Runtime or a database-backed service (Cloud SQL) on Cloud Run ([Cloud Run deploy](https://adk.dev/deploy/cloud-run/)). Third, **secrets** in Secret Manager. Fourth, **data packaging**, appropriate only because the data is synthetic. Fifth, **a front end that authenticates the customer** and passes the verified identifier as the session `user_id` instead of trusting the chat body. IAP suits employees, not retail customers (inference, IAP docs not read). Sixth, **region**: Cloud Run and Agent Runtime support Montreal and Toronto, Memory Bank only Montreal, and Gemini 3.8 Flash is GA in `northamerica-northeast1` on Vertex since 9 November 2026 ([agent locations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/agent-locations); [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)). Seventh, **telemetry and `min-instances`**, since loading a numpy index at import time lengthens cold starts. Eighth, **CI and evals**. No official migration time was found, and no source on cold-start latency, quotas or concurrency.

## Costs and time-to-value favor custom, and licensing is the blocker for Gemini Enterprise

Using the notes' stated assumptions (10,000 conversations a month, six turns, about 3,000 input and 300 output tokens per call, no caching), token costs on Gemini API prices ([pricing](https://aistudio.google.com/docs/pricing)) are about **$99 for gemini-3.5-flash-lite, $202 for gemini-3.8-flash through 31 December 2026, $405 for 3.8 Flash from 1 January 2027, and $576 for gemini-3.1-pro-preview**. The price doubling on 3.8 Flash is the largest single swing. Hosting is minor: Agent Runtime at one always-on vCPU and 2 GiB is at most about **$75 per month** at reported SKUs of $0.085 per vCPU-hour and $0.009 per GiB-hour ([price sheet via search summary](https://services.google.com/fh/files/emails/b_502770571_gemini_enterprise_agent_platform_pricing.pdf)). Cloud Run is about $31 at unverified rates. Totals are about **$130 (Flash-Lite on Cloud Run), $174 (Flash-Lite on Agent Runtime) and $480 (3.8 Flash on Agent Runtime)**, or $0.013 to $0.048 per conversation. Treat this as an illustration. Cloud Run, logging and Agent Runtime billing granularity were not verified, and retrieval-heavy prompts of 10,000 input tokens would raise Flash-Lite to about $330. The estimate excludes engineering time, which dominates real cost.

| | Gemini Enterprise only | Custom ADK only | Hybrid (ADK registered in Gemini Enterprise) |
|---|---|---|---|
| Customer-facing use | Not confirmed licensable for external users; seats are per employee | Yes, behind your own front end | Customers via your front end, staff via seats |
| Per-user authorization in code | Index ACLs and workforce identity; code-side only via MCP or ADK hosted by you | Full control; principal from verified front end | Same code; staff principal arrives as platform-forwarded token (mechanics unverified) |
| Confidence gating A-E and validator loop | Not native; needs an MCP tool or ADK agent | Native | Native inside the registered agent; UI behavior unverified |
| Fixed five-agent pipeline | Lost with MCP route (platform LLM picks tools) | Kept | Kept if the whole ADK app is registered |
| Cost at 10,000 conversations | Per-seat plus $0.10 per query overage; roughly $6,000 if misapplied to customer volume | About $130-$480 per month plus engineering | Custom cost plus seats |
| Ops burden | Lowest (Google-managed) | Highest (evals, guardrails, on-call, persistence) | Highest plus registration and quota management |
| Time to value (my estimate) | Days to 1-2 weeks for internal assistant | 4-10 weeks from scratch, shorter here since the prototype exists | Custom plus about 1-2 days to register, if prerequisites hold |

On licensing, the editions page says nothing about external users, a user must hold a license to sign in, and self-serve and resold accounts are capped at 25 seats per account and invoiced accounts at 1,000 ([editions docs](https://docs.cloud.google.com/gemini/enterprise/docs/editions); [licenses docs](https://docs.cloud.google.com/agentspace/docs/licenses), search snippet). Registration exposes an agent only to users within a Gemini Enterprise app ([register ADK agents](https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-adk-agent)). That makes the hybrid a staff surface. The customer-facing Google product is Gemini Enterprise for Customer Experience (CX Agent Studio), at about **$0.50 per session** ($0.40 on a three-year plan), with a chat session billing again after 50 turns or 30 minutes of inactivity ([CX Agent Studio pricing](https://cloud.google.com/products/gemini-enterprise-for-customer-experience/cx-agent-studio/pricing), search snippet). That is roughly **$4,000 to $5,000 per month** at 10,000 conversations, with evaluation and monitoring included. Under its terms the customer remains solely responsible for supervising agents ([GECX terms](https://cloud.google.com/terms/gecx), search snippet), so managed does not mean accountable for you. Canada adds a constraint: residency needs allowlist access, and only Gemini 3.5 Flash among the Flash models is supported in `ca`. Enabling an unsupported model silently routes to the `global` endpoint with no residency ([locations](https://docs.cloud.google.com/gemini/enterprise/docs/locations)). The free AI Studio key has no evidenced residency guarantee at all.

## What is unverified, and what needs a proof of concept or written confirmation

The items below carry the decision. The first five need written confirmation from Google. First, **whether external, non-employee users may hold Gemini Enterprise seats**, which no readable terms text settles. Second, **official per-seat prices and Plus pricing** (the pricing page returned 404, and Plus is $30 against $50 by source). Third, **which editions include "full-code agents built outside Gemini Enterprise"** and which support `ca`. Fourth, **the GA label for the tool-authorization resource and for sharing registered agents**. Fifth, **Agent Runtime and Cloud Run SKUs**, since the Agent Runtime figures come from a search summary of a PDF that would not parse and the Cloud Run figures are model recall.

Four items need a proof of concept of roughly one to two days on a billed project. The first is the **identity hand-off**: register the ADK agent with and without an authorization, log what lands in session state and `user_id`, and confirm the email claim against the maintainers' "no end-user information" answer. Second, **fail-closed behavior** when no token arrives, and the claim set per identity provider. Third, whether **Sequential and Loop agents, callbacks and a custom `BaseAgent` run unchanged**, how intermediate events display, and the chat-turn timeout and latency of a five-agent pipeline. Fourth, **bundling the numpy index** on Agent Runtime. Smaller unknowns: the Business seat cap (300 against 500, with Google's 500 preferred), the MCP action cap (100 against 150), `rankSignals` ranges and whether they populate for ingested data, Agent Runtime free tier, and whether Agent Runtime compute bills only while active. Several source pages were read through a small-model summary or search snippets, so wording is paraphrased and each claim marked "snippet" should be re-read at source.

## Conclusion

The comparison is less build versus buy than a question of which layer owns the principal. Gemini Enterprise's strength, permission-aware search for employees, depends on the platform holding identity and ACLs, which is the opposite of the prototype's rule that code holds the principal and the model never sees it. Google's own architecture sends per-user decisions back to code you host, through a bearer token on an MCP or A2A request or a token in ADK session state. So the code asset that matters is the prototype's guard, composite and tools, and it is worth keeping in any option. The newly GA registration, A2A and Custom MCP paths make a later hybrid plausible, but they do not remove the need to build and test the identity hand-off yourself.

The practical sequence is to ship the custom ADK agent first, on Cloud Run or Agent Runtime in a Canadian region, with a paid or Vertex model and persistent sessions. Run the one-to-two-day registration proof of concept and send Google the licensing question before committing any seat budget. If Google confirms external seats are permitted, the hybrid is cheap to add. If not, the realistic alternatives for a customer-facing channel are the custom build or the roughly ten-times-costlier per-session product. Gemini Enterprise only never becomes the answer for this use case under the evidence gathered.
